# n8n Workflow — CSV to PostgreSQL

The importable workflow is [`csv-to-postgresql.json`](csv-to-postgresql.json). Its n8n workflow name is **CSV to PostgreSQL**. It reads one selected project CSV per manual run, validates the rows, routes on the exact filename, inserts accepted rows into the matching `supply_chain` table, exposes rejected rows on a dedicated review branch, and records the batch counts in `supply_chain.load_audit`.

All source records are generated by `src/generate_synthetic_dataset.py`. Use only `data/synthetic/` for successful loads and the two files under `data/fixtures/` to test rejection. Do not add the tutorial creator’s non-redistributable data.

## Before import

1. Run `sql/01_create_tables.sql` in the target PostgreSQL database. It creates the five data tables and `supply_chain.load_audit`.
2. Make the repository’s CSV files accessible to the machine or container running n8n. The workflow’s initial `file_path` value is only a placeholder: `/home/node/.n8n-files/supply-chain/data/synthetic/orders.csv`. Change it in **Set Batch Metadata** to the path for the one file you want to load. The path must be valid inside n8n’s runtime, not merely a path on your host computer. For Docker, mount the data directory into the n8n container. n8n 2.x restricts file access by default; grant access only to the project data directory.[1]
3. Import `csv-to-postgresql.json` in n8n using **Workflows → Import from File**.
4. Open each PostgreSQL node and select the same PostgreSQL credential: `Insert Audit Started`, the five `Insert …` nodes, and `Update Load Audit`. The export intentionally contains no credentials.
5. Change the `file_path` field and execute the workflow once for each CSV. Start with the three dimensions, then load orders, then order lines.

The correct order is `customers.csv`, `products.csv`, `carriers.csv`, `orders.csv`, and `order_lines.csv`, because PostgreSQL enforces the foreign keys. The workflow processes one file per execution; it does not scan a folder or run all five files automatically.

## Workflow stages

1. **Manual Trigger** begins an intentional, single-file run.
2. **Set Batch Metadata** holds the configurable path and creates a batch ID and start timestamp.
3. **Read CSV File** reads the selected file from the n8n runtime. **Extract CSV Rows** parses the header row into one item per record.
4. **Validate & Summarize** checks the filename and expected fields, required values, duplicate keys within the file, market/currency rules, ISO dates, status, and numeric quantity/price rules. It retains row numbers and reasons for rejected records.
5. **Insert Audit Started** records the batch, input row count, validation rejection count, and `started` status in the existing audit table.
6. **Has Rejected Rows?** sends any invalid records to **Rejected Records — Review in Execution**. Inspect that node’s output to see the rejected row contents and reasons. This simple version does not create a separate rejection table or write a rejection file; the audit stores a bounded error summary, while the rejection branch preserves the detailed records in the n8n execution output.
7. **Has Valid Rows?** bypasses table routing when no rows passed validation. Otherwise **Route by Filename** sends the rows to the matching table branch. The five supported file names are `customers.csv`, `products.csv`, `carriers.csv`, `orders.csv`, and `order_lines.csv`.
8. Each branch strips workflow metadata before its matching PostgreSQL insert. Inserts use automatic column mapping and transaction batching. The PostgreSQL table constraints enforce database types, primary keys, unique line positions, and foreign keys.
9. **Update Load Audit** marks a completed run `succeeded`, with the successfully inserted count and validation-rejected count. If a table insert fails, its transaction is rolled back and the failure branch updates the audit to `failed` with `accepted_rows = 0`. If PostgreSQL is unavailable, even the audit update may fail; the batch then remains `started` until you can inspect and correct it.

Unknown filenames are not inserted. Empty values are only converted to SQL `NULL` by the PostgreSQL node so the blank `actual_delivery_date` on cancelled orders can load correctly. Do not use “skip on conflict”: an existing primary-key conflict should remain visible and fail the batch instead of silently understating the load.

## Validation boundaries

The workflow validates each file’s row shape and local field rules. It cannot fully verify cross-file references before insertion. PostgreSQL remains the final authority for foreign keys and conflicts with rows already in the database. Load the dimension tables before fact tables. If a database constraint fails, the file insert is transactional and the batch should be marked failed rather than partially accepted.

File-path or CSV-parser failures occur before the workflow has a parsed batch summary, so no `load_audit` row can be written for those failures. Inspect the n8n execution details and correct the path or file before rerunning.

The rejection branch is for review in n8n’s saved execution data. If you need durable rejection storage later, add an explicitly permissioned file/cloud-storage destination or a reviewed rejection table; do not assume execution history is a long-term archive.

## Quick test plan

- Use a clean database and import all five clean CSVs, one file per run, in dependency order. Confirm audit counts and table counts match the CSVs.
- Execute each validation fixture by setting `file_path` to the fixture path. Confirm its invalid rows appear in **Rejected Records — Review in Execution**, its accepted rows are inserted if any, and audit counts reconcile.
- Try an unsupported filename. It should be routed as rejected, not into an analytical table.
- Run a file twice against the same populated tables. A primary-key conflict should fail the insert transaction and be recorded as failed; it must not be reported as a successful duplicate load. For another clean end-to-end run, use a fresh database or reset only this project’s tables after confirming the target database contains no other data.
- If PostgreSQL is temporarily unreachable, the execution should expose the error. The audit row may remain `started` if the database cannot accept the failure update.

## Import artifact checks

The JSON export parses, every connection target resolves to a node in the workflow, and the embedded validation code was exercised against the five generated clean CSVs, both invalid fixtures, and an unsupported filename. Those validator checks passed. The workflow has not been run inside your n8n instance or against your PostgreSQL credentials. After import, you still need to set the runtime file path and credentials, run the SQL setup, and complete the end-to-end tests above.
